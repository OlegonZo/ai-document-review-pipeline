# AI Document Review Pipeline

[![Tests](https://github.com/OlegonZo/ai-document-review-pipeline/actions/workflows/tests.yml/badge.svg)](https://github.com/OlegonZo/ai-document-review-pipeline/actions/workflows/tests.yml)

Честный демонстрационный проект для портфолио: входящий документ проходит через классификацию, бизнес-правила и сохраняется в SQLite. Надёжные случаи получают статус `ready`; спорные попадают в очередь `review`. Каждое решение сопровождается журналом причин.

> Это локальный demo-проект на синтетических данных. Он не подключён к банкам, 1С, Telegram или LLM-провайдерам и не заявляет измеримый коммерческий эффект.

## Что показывает проект

- HTTP webhook для приёма документов;
- явное разделение классификации и бизнес-правил;
- правила ручной проверки: низкая demo-уверенность, отсутствующий контрагент, невалидная сумма и неподдерживаемая валюта дают статус `review`;
- документы и журнал решений в SQLite, сохраняемые в одной транзакции;
- пример n8n: webhook → HTTP API → проверка статуса `review`;
- тесты бизнес-правил, журнала, транзакционного отката и сохранения данных; CI на Python 3.11–3.13.

## Что посмотреть работодателю

1. [app/main.py](app/main.py) — HTTP-контракт, входная валидация и выборка записей.
2. [app/domain.py](app/domain.py) — интерфейс классификатора и независимые бизнес-правила.
3. [app/repository.py](app/repository.py) — транзакционная запись документа и события журнала.
4. [tests/test_service.py](tests/test_service.py) — проверка содержимого журнала, маршрутизации и поведения при сбое записи.

Инженерная идея: классификация предлагает данные, а явные правила решают, можно ли продолжать обработку. Статус `review` означает запись для ручного разбора, а не готовый интерфейс оператора.

## Схема

```text
Документ / webhook
        │
        ▼
Классификатор (demo adapter)
        │
        ▼
Правила валидации ──► записи review (для ручного разбора)
        │
        ▼
      ready
        │
        ▼
SQLite + audit log
```

## Быстрый запуск

Требуется Python 3.11 или новее. Команды ниже выполняются из корня скачанного репозитория. Если команда `python` недоступна в Windows, используйте установленный Python через `py` или полный путь.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
uvicorn app.main:app --reload
```

После запуска откройте `http://127.0.0.1:8000/docs`.

Пример запроса:

```powershell
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/webhooks/documents `
  -ContentType 'application/json' `
  -Body '{"source":"demo","text":"Оплата счёта ООО Ромашка 12500 RUB"}'
```

Проверить очередь исключений:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/records?status=review
```

## n8n

Файл [workflows/document-review-webhook.json](workflows/document-review-webhook.json) можно импортировать в n8n. Он иллюстрирует передачу документа в API и развилку `ready/review`; URL и учётные данные намеренно не встроены.

Замените `YOUR_PIPELINE_HOST` на адрес API, доступный из n8n. Узла отправки уведомлений в примере нет; его нужно добавить под выбранный канал. Импорт и выполнение workflow в реальном n8n не проверяются текущим CI.

## Границы текущей реализации

- `DemoClassifier` разбирает текст детерминированно, не вызывает LLM и не измеряет статистическую уверенность модели.
- Название контрагента извлекается из текста; сверки с реестром известных контрагентов нет.
- `audit_events` — обычная таблица журнала, без защиты от изменения администратором БД.
- Повторный POST создаёт новую запись: идемпотентность и дедупликация пока не реализованы.
- Нет аутентификации HTTP API, retry-очереди и производственной обработки персональных данных. Запускайте локально с синтетическими примерами, не публикуйте открытый API.

## Как развивать проект

1. Заменить `DemoClassifier` на адаптер конкретного LLM с таймаутами и логированием версии модели.
2. Добавить аутентификацию webhook и хранить секреты вне кода; переменные окружения сами по себе не являются шифрованием.
3. Добавить внешний ID события, идемпотентность, HTTP-интеграционные тесты, повторные попытки и метрики очереди; при необходимости перейти на PostgreSQL.
4. Перед реальным использованием согласовать правила с владельцем процесса и измерить baseline на обезличенных данных.
